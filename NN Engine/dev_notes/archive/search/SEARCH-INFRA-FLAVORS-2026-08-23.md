# Search / infrastructure flavors + why OURS underperform (2026-08-23)

**The reframe that owns this doc (owner, 2026-08-23):** we already have most of these features — killers, history, a gated correction-history, TT, SEE, aspiration windows — and they've *failed or underperformed* for us (search is ~2-for-15 in games). But the strongest open-source engines all use these exact things and gain from them. **So the problem is almost certainly that we're using them WRONG** — wrong location, untuned, or dismissed after a flawed test — not that the techniques are weak. The forward job (after the KS/passer arc) is to **audit our implementations against the engines that succeed and find where they diverge**, exactly as the de-biased-regret work reopened "closed" eval lanes. Sources: fable web survey of Stockfish/Ethereal/Weiss/Stormphrax/Viridithas/Berserk/Gyatso, 2026-08-23 (raw source reads, cited inline).

## 0. Confirmed NON-levers (stop chasing these)
- **SIMD** — overwhelmingly NNUE only (accumulator add/sub + int matmul). NO strong engine vectorizes a hand-crafted eval or the search. SF's TT probe is a scalar 3-entry loop; Ethereal's HCE is scalar `popcount/poplsb` throughout. The only relevant HW acceleration for HCE+search is **POPCNT / BMI2-PEXT / prefetch / cache-line layout** (we already compile `-mbmi2 -mpopcnt`). SIMD becomes relevant ONLY at the NNUE stage (then `bullet` hands it to you).
- **Move generation** — magic vs PEXT vs hyperbola-quintessence are real but movegen is ~1.4–30% of runtime (usually a few %). Community verdict: micro-opt buys "a few % at best." With OUR profile = **eval 65–84% of node cost** ([[speed-and-qsearch-findings-2026-07-24]]), movegen is a confirmed non-lever. Node-count reduction (ordering/pruning) beats NPS from movegen — our [[bound-the-mechanism-not-a-proxy]] rule.

## 1. The REAL levers (history/ordering/caching), ranked by expected return
Field has hard-converged; all forms below verified in source. Port FORMS, refit CONSTANTS.

1. **★ CORRECTION HISTORY (static-eval correction) — the headline for US.** Table keyed by pawn-structure hash (then nonpawn-material-per-side, major-piece, continuation) accumulating `(searchScore − staticEval)` × depth (gravity update), which **corrects the static eval BEFORE it feeds RFP / futility / stand-pat**. Origin Caissa Oct-2023; now in SF, Weiss, Stormphrax, Berserk, Motor, Sirius (CPW "Static Evaluation Correction History"). **NOT NNUE-specific — Weiss runs it on a pure HCE.** Why it fits us uniquely: it corrects the eval's *net output per position-class* WITHOUT re-weighting terms → **orthogonal to our eval degeneracy** (every magnitude retune flattens; corrhist doesn't touch magnitudes). It targets exactly the Stage-3 margin arithmetic our [[three-stage-subsystem-audit]] flagged, and our diagnosed "every term flips sign" calibration errors. ⚠️ **We already have `ENABLE_CORR_HIST=0` (CORR_SHIFT=6 CORR_MAX=2000 CORR_W=192 CORR_DIV=256) gated OFF, and memory `corrhist-qsearch-harmful-and-qcache-masks-eval` says we tried corrhist IN QSEARCH and it hurt.** But the valuable form is **static-eval correction feeding pruning margins** — a DIFFERENT location. Prime suspect for a prematurely-closed lane: verify what our impl actually does; if it's qsearch-only, the static-eval-pruning form is untested. Ref: Weiss `src/history.h`; SF commit b4d995d (canonical minimal); Stormphrax `src/correction.h` (4-key mature form).
2. **Continuation history at 1–2 ply** — biggest tree-shrinker if we lack it or it's shallow; it's what makes LMR's move-index keying sound (our notes flag the LMR-index interaction). Returns: 1-ply ≫ 2-ply ≫ 4/6-ply tails. Refs: Weiss (1,2,4), Ethereal (1,2), SF movepick offsets {1,2,3,4,6}.
3. **Threat-indexed main history + explicit MALUS** — now the STANDARD form of butterfly history (`[stm][from][to][threat_from][threat_to]`), not a Gyatso novelty (Ethereal/Stormphrax/Berserk all have it). Needs a per-node threatened-squares bitboard = cheap for us (HCE already computes attack maps). The gravity update `entry += bonus − entry·|bonus|/LIMIT` + a **malus** for quiets that failed to cut is a known gainer if we lack the self-decaying/malus form. Ref: Ethereal `src/history.c` (clearest didactic impl).
4. **Pawn-king EVAL CACHE** — the classical HCE speed structure (SF11 `pawns.h` 131072-entry table caches pawn scores + passed-pawn bitboards + **king shelter/safety** as ONE unit; Ethereal PKTable same). Direct hit on our 65–84% eval cost, and **exact by construction** (pure function of pawn+king placement) so it dodges the qcache-masks-eval failure mode. Lives exactly as long as the HCE does. Ref: `raw .../Stockfish/sf_11/src/pawns.h`, Ethereal PKTable.
5. **Capture history feeding SEE-prune thresholds** — synergizes with our shipped SEE-captures; modern form adds a defended/threat flag. Refs: Ethereal/Stormphrax/Weiss capture-hist tables.
- Killers/countermoves: newest engines (Stormphrax) DROP them as redundant with conthist — keep whichever ablation supports, don't stack both.

## 2. Aspiration windows — audited 2026-08-23 (implementation CORRECT, just under-tuned)
Our root aspiration loop (search_engine.cpp ~2564) is a **correct textbook implementation**: root-only (no leakage into internal PVS scouts — the owner's suspected α/β-inside-search bug is NOT present), asymmetric widening (widens only the failing side, keeps the other bound tight), guarded by `HONEST_ROOT_TT` (on by default — required for sound TT bounds), near-mate skip, full-window fallback after `ASPIRATION_MAX_WIDENINGS`. **The weakness is purely tuning:** `ASPIRATION_DELTA=500` (±0.5 pawn) is WIDE → rarely fails → buys little depth ("helped but not huge" = exactly this signature). Gyatso corroborates: its window is ±20cp, tight. SF11 uses `delta += delta/4 + 5` from a small start. There's also a small win available (on fail-high, raise `alpha_win` to the old `beta_win` for a tighter re-search) and a fail-high depth-reduction idea (Gyatso caps at −2 ply).
- **Built-in diagnostic already exists:** `g_asp_windows / g_asp_fails / g_asp_fallbacks` to stderr per move (line ~2665). Target fail rate ~10–30% (near-0% = too wide = wasted).
- **TUNING METHOD (search-efficiency items generally): fixed-NODE-budget screen → fixed-TIME games.** Fixed DEPTH is BLIND to efficiency (aspiration reaches same depth in fewer nodes → no change). Fixed TIME is the right metric but machine-noise-sensitive (subtle state shifts swing low-time evals — our [[nps-ruler-is-too-blunt]] / [[warm-state-blindness-in-all-benches]]). **Fixed NODE BUDGET (`NODE_LIMIT=N`) is the deterministic middle:** aspiration reaches deeper at the same nodes → efficiency becomes visible, node counts are exact/machine-independent, and re-search cost is auto-charged (a too-tight window that fails often scores worse). Screen DELTA values there; games at fixed TIME are the noisy-but-self-averaging arbiter.

## 3. HCE→NNUE pipeline (the owner's endgame) — the well-trodden path
- **Viridithas is the cleanest template:** PeSTO HCE → Texel-tuned HCE → first NNUE trained on games played by its OWN HCE → every later net on self-play of the previous net. In-engine datagen (no book needed).
- **Recipe:** self-play at ~5,000-node soft limit/move, 8–10 random opening plies, save `(FEN, search score, game result)`; filter positions in-check / best-move-is-capture / very-early / near-mate; first usable net ~100M positions; architecture = perspective **768→N×2→1** (N 256–1024, CReLU/SCReLU), no buckets until net #2; trainer = **[bullet](https://github.com/jw1912/bullet)** (Rust GPU, de-facto standard), WDL/score blend lambda ≈0.7; iterate.
- ⚠️ **Honest challenge to "2800–3000 HCE first":** the field's experience (Viridithas from a *mediocre* HCE, Stormphrax from *zero*) is nets from 2200–2500-strength labels already leapfrog their teacher — label quality is dominated by **volume + filtering, not teacher Elo**. "2800 first" is a fine *search-quality* goal (search carries into the NNUE engine 1:1) but is NOT a prerequisite for a strong first net. Self-play data we're already banking is the real asset.

## 5. Forward plan (after KS/passer arc)
Audit our search-feature implementations against Weiss/Ethereal to find the "using it wrong" divergences, in return order: **(1) corrhist — verify ours is/ isn't static-eval-feeding-pruning; the qsearch null may be a wrong-location artifact; (2) conthist depth — do we have 1+2 ply?; (3) threat-index + malus on main history; (4) pawn-king eval cache for the 65-84% eval cost; (5) capture-hist → SEE-prune.** Then aspiration tuning via the fixed-node-budget method. Each judged at fixed TIME on diverse games; screen efficiency deterministically on node budget first. Non-levers (SIMD, movegen) stay parked until NNUE.
