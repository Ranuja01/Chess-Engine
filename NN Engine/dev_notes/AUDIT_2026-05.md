# Engine audit — May 2026

Independent, code-level verification of bug claims raised in a Gemini chat about the C++ engine, plus an additional sweep. Each claim was checked against the actual source, not the summary. **Lesson reinforced throughout: verify against the code's real (often non-standard) conventions before trusting a claim.**

## Verdicts on the Gemini claims

| Claim | Verdict | Detail |
| --- | --- | --- |
| Minimax "sign-flip" / root always maximizes the wrong perspective | **BOGUS** | Eval is absolute (positive = Black advantage). `minimizer` is a genuine min-node (`lowest_score`, `beta = min(beta, lowest_score)`, cut on `beta <= alpha`); `maximizer` a genuine max-node (`alpha = max(alpha, highest_score)`, cut on `beta <= alpha`). Root maximizes and calls `minimizer`; a single global flip via `Config::side_to_play` in `get_board_evaluation`. Internally consistent — matches the ~2700-Elo empirical result. |
| Minimizer null-window uses `[alpha, alpha+1]` instead of `[beta-1, beta]`; "invalid TT flags / hallucinated scores" | **MISCHARACTERIZED** | `get_score_for_minimizer` and `get_score_for_maximizer` are byte-symmetric: both scout with `[alpha, alpha+1]` and re-search when `score > alpha && score < beta`. Traced every case: this is **correct** (re-search recovers exact values; out-of-window cases resolve to sound bounds). TT flags stored are consistent with the `[alpha, alpha+1]` window actually used — **not** invalid. It *is* a genuine **efficiency** opportunity (min-nodes lose PVS narrowing; non-improving children get full re-searched). → deferred experiment, must be A/B-measured. |
| Queen value 9000 (pyx) vs 10000 (C++) inconsistency | **TRUE but FUNCTIONALLY BOGUS** | `values[]` in `ChessAI.pyx` (lines ~151–158) is **dead code** — never referenced. SEE uses the C++ `values` (queen 10000) via `get_value_at`. No effect on play. (Knight 3150 vs 3250 likewise dead.) |
| **Bug 1** — deque duplication in `addToCache` / `addToSearchEvalCache` | **REAL** (fixed) | `push_back` to the FIFO deque was unconditional, so updating an existing key appended a duplicate. Result: hot keys accumulate stale deque copies → premature eviction of the live entry + map/deque desync (map can exceed `max_size`). Correctness-neutral (caches), perf/memory. Bites mainly in **long games** where eviction fires; the 16.6s baseline never reaches `max_size`. **Fix:** only `push_back` when the key is new. |
| **Bug 2** — dead branch in `updateMoveCacheForBetaCutoff` | **REAL, LOW-impact** (fixed) | `if (moveEntry.key != updatedKey)` could never be true because `accessMutableMoveGenCache` stamps the key before returning. So on a (collision) miss the passed-in move list was discarded and an empty list stored. Impact limited: only on direct-mapped collisions, the empty list is treated as a miss by `buildMoveListFromReordered` (`size != 0` check) and **self-heals** on next access; the common no-collision path already worked. **Fix:** read the slot directly and detect the miss before overwriting, then store the list (cutoff move promoted to front). |

## Additional sweep findings

- **`move.promotion == 1` LMR gate is CORRECT.** Move generation encodes "no promotion" as `1` (`move_gen.h` push_backs of `1` for normal/castle/EP moves; promotions push the piece type 2–5). So gating LMR on `promotion == 1` correctly means "quiet, non-promotion move." Non-standard encoding, used consistently. (The Python-facing `MoveData` defaults promotion to `0`, but generated `Move`s always set it explicitly — a cosmetic default mismatch, not a live bug.)
- **`use_tt_entry`'s unused `is_maximizing` param is FINE.** The bound logic (EXACT always; LOWERBOUND if `score >= beta`; UPPERBOUND if `score <= alpha`) is correct for both node types because the engine stores *absolute* bounds. Ignoring the param is correct.
- **`evalCacheNew`** (direct-mapped `std::vector<EvalEntry>`, `cpp_bitboard.cpp:70`) exists but is unused — an in-progress migration away from the `unordered_map` + `deque` scheme. Signals the intended direction for the deferred cache refactor.
- **Hot-path debug `std::cout`** blocks gated by magic `current_state.occupied == <constant>` conditions are scattered through `minimizer`/`maximizer`/eval. They rarely fire, but the comparison runs every node — minor overhead and clutter.

## Executed (2026-05-28)

Both fixes confined to `cache_management.h`; no eval or move-gen logic touched.

- **Bug 1:** guarded the deque `push_back` in `addToCache` and `addToSearchEvalCache` with an `isNewEntry` check.
- **Bug 2:** rewrote `updateMoveCacheForBetaCutoff` to read the slot directly (`updatedKey & CACHE_MASK`) and stamp key/valid on the miss path so the move list is stored instead of discarded.

See [BASELINE_PERF.md](BASELINE_PERF.md) for the pre-fix reference and the regression-check methodology (compare per-depth PV/score tables at equal depth).

## Deferred follow-ups

1. **Minimizer PVS window** `[alpha, alpha+1]` → `[beta-1, beta]` with re-search on `score < beta`. Real upside, hottest path — needs A/B measurement vs baseline.
2. **Cache migration** of `evalCache` / `searchEvalCache` from `unordered_map` + `deque` to direct-mapped arrays (like `evalCacheNew` / `moveGenCache` / `quiesceEvalCache`). Eliminates Bug 1 by design; removes hashing/allocation overhead. Larger refactor.
3. **Cleanup:** remove dead `values[]` in `ChessAI.pyx`; strip or compile-out the magic-constant debug `std::cout` blocks in the search loop.
